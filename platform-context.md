# Контекст проекта: платформа акций и челленджей (Tasker)

_Источники: «Жизненный цикл SDLC» (docx), «Топология и архитектура платформы акций» (PDF, 7 слайдов), ebobo.sql (схема БД, версия 2 от 2026-11-19). Дата записи: 2026-11-11, обновлено 2026-11-19._

## 1. Суть проекта
- Веб-сайт, где пользователи ищут акции и челленджи и получают за них вознаграждение.
- **Важно:** сами челленджи/акции проходят НЕ на платформе. Платформа — только каталог объявлений. Пользователь переходит на внешний «ключевой источник» (пост в соцсетях или страница с условиями акции).
- Компании размещают объявления (акции и челленджи; **опросов на сайте не будет** — упоминание в SDLC-документе ошибочное). Награды выдают и оплачивают компании.
- Роли: **пользователь**, **компания**, **администратор**.
- Проект учебный: финальный этап — защита перед преподавателем. Бюджет шуточный: «пачка сухариков и банка спрайта».

## 3. Процесс (SDLC)
- Итеративная и инкрементная модель, спринты 2–3 недели; в конце спринта — закрытое законченное ТЗ на спринт.
- Канбан-доска в Jira.
- Этапы: 1 Планирование → 2 Анализ требований → 3 Проектирование → 4 Разработка → 5 Тестирование → 6 Развёртывание → 7 Защита и сопровождение.

### План спринтов
- **Спринт 1:** репозиторий; дизайнер учит Figma и UI/UX; бэк учит Node.js + Express; фронт создаёт дизайн-систему.
- **Спринт 2:** сущности и таблицы БД, авторизация на бэке; набросок главной (лендинг) и страницы авторизации в дизайне и на фронте.
- **Спринт 3:** API объявлений; страница каталога; страница личного кабинета.
- **Спринт 4:** админ-панель и модерация, защита от поддельных объявлений, доработки.
- **Спринт 4.5:** тестирование и доработка. Результат — рабочий MVP.

## 4. Требования MVP
Функциональные:
- Регистрация и авторизация для всех ролей.
- Безопасное хранение паролей и персональных данных.
- CRUD объявлений об акциях (роль «компания»).
- Личный кабинет пользователя; кабинет компании (свои посты об акциях/челленджах); кабинет администратора (модерация компаний и объявлений, управление пользователями).

Нефункциональные:
- Адаптивный интерфейс (телефон и ПК).
- История активностей пользователя.

## 5. Стек
- Frontend: React + TypeScript (опц. Tailwind CSS)
- Backend: Node.js + Express
- БД: PostgreSQL
- Авторизация: JWT + bcrypt, роли и права доступа
- Дизайн: Figma; код: GitHub (ветки + pull request); задачи: Jira
- Тесты: Jest, Postman
- Деплой: Render / Railway / Vercel / VPS (HTTPS, env-переменные, демо-аккаунты трёх ролей)

## 6. Архитектура (из PDF)
Три звена: клиент (браузер) ↔ сервер ↔ данные. Браузер напрямую в БД и файлы не ходит — единственная точка входа сервер.

Связи:
- Браузер ↔ сервер: HTTPS, JSON (REST API)
- Сервер ↔ PostgreSQL: SQL, драйвер `pg`; **6 таблиц** со связями
- Сервер ↔ папка `uploads`: файловая система; в БД только путь к файлу
- Администратор → реестр БИН (stat.gov.kz): вручную в браузере, сверка БИН компании

Модули сервера (Node.js + Express):
- **Авторизация:** регистрация, вход, JWT, bcrypt, проверка роли
- **Проверка БИН:** 12 цифр + контрольная цифра при регистрации компании
- **Бизнес-логика:** статусы акций и участий; акции, участие, отзывы, жалобы; ~~отзыв можно оставить только после статуса `passed`~~ (устарело: статуса участия больше нет, см. раздел 15)
- **Загрузка фото:** multer, JPG/PNG/WEBP до 5 МБ, проверка типа и размера

БД: ограничения, внешние ключи, ~~триггер для отзывов~~ (в версии 2 схемы триггера для отзывов нет; есть триггер автоблокировки компании).

Роли в потоке:
- Пользователь — участвует в акциях, оставляет отзыв с фото и оценкой
- Компания — публикует акции, статусы, подтверждает прохождение пользователем
- Администратор — проверяет компании, модерирует акции и жалобы

Пример потока «отзыв с фото»: форма (фото, оценка, комментарий) → проверка токена и роли → проверка типа/размера фото → файл в uploads; участие и отзыв создаются одной транзакцией, путь к фото и оценка в PostgreSQL → отзыв виден на страницах акции и компании. (Шаг «проверка статуса участия `passed`» из PDF устарел.)

## 10. Решения владельца (обновлено 2026-11-19)
- **Отзывы с фото — обязательная функция MVP.**
- **Подтверждение прохождения челленджа = оставление отзыва** (с фото участия, оценкой, комментарием). Это и есть способ подтвердить участие.
- **Проверка БИН:** в дизайне должна быть; в реализации — самый последний приоритет (делаем в конце).
- **Прогресс-бары — в личном кабинете КОМПАНИИ** (два штуки):
  1. количество звёздочек (насколько пользователям нравится компания; средняя оценка по отзывам);
  2. количество подтверждённых жалоб на компанию (до 3).
- **Опросов на сайте не будет** (решение владельца).
- Список из 6 таблиц БД владелец дал 2026-11-19 (файл ebobo.sql), см. раздел 15.

### Решения по БД (2026-11-19)
- Запись в `participations` создаётся только если пользователь поучаствовал → **поля status у участия нет** (joined/passed/failed убраны).
- **Компания — отдельный вид пользователя, хранится в своей таблице `companies`.** Связь «один пользователь = одна компания» через `user_id` владелец НЕ хочет; таблица компаний остаётся как в исходной схеме.
- В `promotions` **нет поля типа** (акция/челлендж): само задание в `description`, условия выполнения в отдельном поле `conditions`. **Добавлено поле `address`** (необязательное). **`source_url` обязателен.**
- **Пожаловаться может любой пользователь**, даже если не участвовал в акции. Причины `reward_not_given` в списке нет.
- В отзыве **нет типа награды/`proof_subject`**: пользователь добавляет фото участия, описание и оценку.

### Награда, отзывы и жалобы (бизнес-логика)
- Награду выдаёт **компания** после прохождения челленджа. Награда **напрямую от отзыва не зависит**.
- Зачем нужны отзывы: (1) показывать активность пользователей на платформе; (2) формировать рейтинг компаний; (3) служить подтверждением, что пользователь прошёл челлендж, если награду не выдали.
- Если успешное прохождение подтверждено отзывом, а награды нет — пользователь подаёт **жалобу на компанию** (но жалоба возможна и без участия).
- **Каждую жалобу рассматривает администратор**: одобряет или отклоняет **с объяснением причин** (причина видна/сохраняется).
- **Когда админ подтвердил 3 жалобы на компанию — компания блокируется автоматически.** Считаются только подтверждённые админом жалобы.
- Жалобы также возможны на поддельные объявления (раздел 7): админ может скрыть объявление.
- Нужно будет придумать дополнительную мотивацию для пользователей оставлять отзывы (в будущем, идеи ещё не выбраны).

## 11. Открытые вопросы
- Какая именно награда (промокод, скидка, подарок) и как пользователь её получает — механика на стороне компании, на платформе не отслеживается?
- Сбрасывается ли счётчик подтверждённых жалоб, может ли заблокированная компания быть разблокирована админом.
- Как вход под ролью `company` связан со строкой в `companies` (сейчас в схеме связи нет; возможно, логин/пароль хранить в самой `companies`).
- Участие и отзыв теперь 1:1 (создаются вместе). Оставлять две таблицы (6 по архитектуре) или слить `participations` в `reviews` (будет 5)? Если участие создаётся вместе с отзывом, макет кабинета пользователя (история со статусами и кнопкой «Оставить отзыв») нужно поправить.
- Сделать `promotions.address` обязательным или оставить необязательным (онлайн-челленджи).

## 12. Правила работы над дизайном (Figma)
Порядок, заданный владельцем:
1. Сначала создать **библиотеку токенов** (цвета, типографика, отступы и т.д.) и дальше использовать **только её**.
2. Основные цвета брать из **существующей цветовой палитры в файле Figma** — с готовых компонентов.
3. Отступы — нормальные, на усмотрение дизайнера (Claude).
4. Затем создать **лендинг**, используя только токены стилей.
5. Затем личные кабинеты (компания, пользователь, админ) — по очереди.

## 13. Идеи (мотивация оставлять отзывы)
1. Пользователь оставляет отзыв → получает очки → растёт уровень (виден в профиле). За очки можно покупать «ободки» на фото профиля (как в Discord). Чем выше уровень, тем выше его отзыв в списке отзывов у компании.
2. Компании по желанию могут дать доп. плюшку для активных пользователей.
3. Пользователь делится отзывом с фото в соцсетях, а платформа делает красивую карточку со ссылкой на сайт. Это ещё и бесплатный маркетинг.
4. Быстрый отзыв: оценка звёздами в один тап плюс необязательный комментарий и фото. После перехода на акцию платформа через пару дней напоминает: «Прошли челлендж? Оставьте отзыв».

## 15. База данных: схема ebobo.sql (PostgreSQL, версия 2 от 2026-11-19)
Запуск: `psql -v ON_ERROR_STOP=1 -U postgres -d ebobo -f ebobo.sql`. Скрипт в одной транзакции (`BEGIN … COMMIT`). Расширения: citext, pgcrypto (pgcrypto не используется — bcrypt на Node). Схема ещё не прогонялась на реальной БД.

**ENUM-типы:** user_role (user, company, admin); company_status (pending, approved, rejected, blocked); promotion_status (draft, pending, approved, rejected, hidden, finished); report_status (open, approved, rejected); report_reason_type (impossible_requirements, personal_data_collection, suspected_fraud, branch_closed_or_missing, wrong_reward_info, other).

Русские подписи причин жалоб (на фронте): impossible_requirements — «Невыполнимые требования»; personal_data_collection — «Сбор личных данных»; suspected_fraud — «Подозрение на мошенничество»; branch_closed_or_missing — «Филиал закрыт или не существует»; wrong_reward_info — «Не правильно указана награда»; other — «Другое».

**6 таблиц** (все PK `INT GENERATED ALWAYS AS IDENTITY`):
- `users`: email CITEXT UNIQUE, password_hash, role, full_name, phone, is_blocked.
- `companies`: name, bin CHAR(12) UNIQUE (CHECK 12 цифр), contact_phone, status. Связи с users нет.
- `promotions`: company_id → companies (CASCADE), title, description (само задание), conditions (условия выполнения), address (необязательный), source_url NOT NULL, status, starts_at, ends_at (CHECK ends_at > starts_at).
- `participations`: user_id → users, promotion_id → promotions, joined_at; UNIQUE(user_id, promotion_id). Статуса нет.
- `reports`: promotion_id → promotions, reporter_id → users, reason_type (report_reason_type NOT NULL), description TEXT NOT NULL (≥10 символов), status (open/approved/rejected), admin_comment, resolved_by → users, resolved_at, created_at; UNIQUE(promotion_id, reporter_id). CHECK: если статус не `open`, то admin_comment и resolved_at обязательны. Бэк сам заполняет resolved_at/resolved_by.
- `reviews`: participation_id → participations (UNIQUE, 1 отзыв на участие), rating 1–5, comment, photo_path NOT NULL (CHECK jpg/jpeg/png/webp), created_at.

**Триггер** `trg_reports_autoblock` (AFTER UPDATE OF status на reports): когда жалоба становится `approved`, считаются одобренные жалобы на акции этой компании; при ≥3 компания получает status `blocked`. Если логику решат делать на бэке, триггер можно удалить.
**Представление** `v_reviews`: отзыв + user_id, author_name, promotion_id/title, company_id (для рейтинга компании).
**Индексы:** promotions(status), promotions(company_id), participations(promotion_id), participations(user_id), reports(status), companies(status).

Убрано по решению владельца: тип акции, participation_status, review_proof_subject и поле proof_subject, причина reward_not_given, триггер проверки отзыва, связь companies.user_id.
